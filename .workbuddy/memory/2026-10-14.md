## 诊断：为何"打开还慢" + 提速（1.7.9+140）
- 排查结论：片单**数据层**已秒出（ListCache，1.7.7）；图片慢的根因是**封面必须下载过一次才进磁盘缓存**（`AppImageCache`，2000 张/90 天，已持久化）。首见/新内容（默认"最新"分类每天换新）必走网络，无法避免——这是"打开慢"的真因，不是缓存失效。
- 实现两套提速：
  1. 新增 `lib/utils/image_prefetch.dart`：`ImagePrefetch.prefetch(urls)`，后台抢先把封面拉进磁盘缓存；并发上限 6（避免一次性几十请求挤爆源站），URL 去重。
  2. `film_page` 的 `CategoryTab._load`（读缓存后）与 `_refresh`（刷新后）都 `unawaited(ImagePrefetch.prefetch(...))` —— 本次滚动/下次打开直接读本地不再转圈。TabBarView 各分类 tab 都会触发，覆盖面全。
  3. 网格封面 `video_card.dart` 加 `memCacheWidth: 480`，详情大图 `detail_page.dart` 加 `memCacheWidth: 600`：限制解码尺寸，降内存与首屏解码耗时、滚动更跟手。
- 版本号四处同步 1.7.9+140。单进程静态检查 0 error/0 warning/0 lint。本地提交（未推送）。
- ⚠️ 说明：拼多多式"秒显"靠预取+持久缓存逼近；但**从未下载过的封面首次仍必须联网一次**，这是硬限制。

## 修复：播放页/详情页收藏状态不一致 + "添加失败→成功" 鬼畜（1.7.11+142）
- 现象：播放页收藏后返回详情页显示"未收藏"；再点收藏提示"添加收藏失败"，再点又"收藏成功"。
- 根因：收藏状态缓存在页面本地 `_starred`，只在 `initState` 查一次；从播放页返回时详情页 State 不重建，`_starred` 过期。于是以"未收藏"身份对**已存在**的 key 调 `addStar` → `ZyDatabase.add` 遇重复 key 直接 `return false`（第57行）→ "添加收藏失败"，随后 `_checkStar` 又把 `_starred` 刷新成 true，下一击变成 remove。
- 修复：`detail_page`/`play_page` 的收藏显示改 `context.watch<AppState>().isStarred(_recordKey)` 实时跟随；`_toggleStar` 以权威的 `isStarred` 为准，不再信任过期本地 `_starred`；删除 `_starred` 字段与 `_checkStar()`。`addStar` 对既有 key 返回 false 属预期，不再被误触发。
- 版本号四处同步 1.7.11+142。单进程静态检查 0 error/0 warning/0 lint。
